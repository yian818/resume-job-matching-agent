## P0阶段：基础版搭建

### Bug 1：DeepSeek API认证失败

**现象**：调用API直接报401错误，说API Key无效。

**原因**：用了官方地址`api.deepseek.com`+旧Key，但这个Key是第三方代理平台的，不是官方的。

**修复**：换成第三方代理地址`https://nb.deepsb.com/v1`，Key从`.env`文件读取。

**面试话术**：
> "初版我直接用了DeepSeek官方API，但发现Key是代理平台的，连不上。我改成了从.env文件读取配置，支持切换不同的API地址，这样测试环境和生产环境可以用不同的Key，不用改代码。"

---

### Bug 2：Windows路径转义错误

**现象**：运行时报`SyntaxError: (unicode error) 'unicodeescape'`，指向PDF文件路径那一行。

**原因**：Windows路径里的反斜杠`\`被Python当成转义字符，比如`\U`被当成Unicode转义。

**修复**：路径前加`r`前缀变成原始字符串：`r"C:\Users\...\简历.pdf"`

**面试话术**：
> "Windows开发常见坑，路径里的反斜杠会被Python转义。我用r前缀解决，这是Windows开发的基本功。"

---

### Bug 3：大模型输出JSON不稳定

**现象**：有时候大模型返回`{...}`正常，有时候返回```json {...} ```代码块包裹，有时候返回Markdown列表，导致Pydantic校验失败。

**原因**：大模型是概率性输出，temperature=0.2也不能保证100%格式正确。

**修复**：加了三层降级：
1. 优先走`with_structured_output`结构化输出
2. 失败后手动调LLM，剥掉```json```代码块
3. 再失败就重试一次

```python
try:
    result = structured_llm.invoke(prompt)
except Exception:
    raw = llm.invoke(prompt).content
    raw = raw.replace("```json", "").replace("```", "").strip()
    result = ResumeInfo(**json.loads(raw))
```

**面试话术**：
> "我在评测中发现DeepSeek偶发返回markdown代码块包裹的JSON，导致Pydantic校验失败。我加了一层try-except降级：优先走structured output，失败后自动走raw调用+手动清洗，保证鲁棒性。这是生产环境必须做的，不能假设大模型每次都乖乖输出格式。"

### Bug 4：岗位分析遗漏

**现象**：岗位列表有3个，但大模型只分析了2个就停了。

**原因**：长文本注意力衰减，大模型处理长列表时容易漏最后几个。

**修复**：三层优化：
1. temperature从0.2降到0.1，降低随机性
2. 岗位列表从JSON改成编号文本格式（1. 岗位名...）
3. prompt里明确写"共N个岗位，必须逐个分析完"

**面试话术**：
> "初版测试发现大模型只分析了2个岗位就停了，这是长文本注意力衰减问题。我做了三层修复：温度调低、列表编号化、prompt里强调必须逐个分析完。修复后3个岗位全部覆盖。"

### Bug 5：条件分支不生效

**现象**：信息缺失时没有走追问节点，还是直接走了匹配节点。

**原因**：三个地方没对齐：
1. `state.py`里没有`info_complete`字段
2. `nodes.py`里没有判断逻辑
3. `main.py`里`add_conditional_edges`注册了但判断函数永远返回`match_jobs`

**修复**：
```python
# state.py 加字段
info_complete: bool

# nodes.py 加判断
state['info_complete'] = result.work_year > 0

# main.py 加条件分支
def should_match(state):
    return "match_jobs" if state['info_complete'] else "ask_more"

workflow.add_conditional_edges("extract_resume", should_match, {
    "match_jobs": "match_jobs",
    "ask_more": "ask_more"
})
```

**面试话术**：
> "条件分支没生效，我debug后发现是三层没对齐：state里没定义字段、node里没判断、graph里注册了但判断函数写死了。改完后测试：信息缺失走追问，信息完整走匹配，分支逻辑验证通过。LangGraph的条件分支关键是state字段要贯穿全链路。"

## P1阶段：评测体系

### Bug 7：education输出太啰嗦

**现象**：模型输出"华中科技大学自动化专业2016届"，标准答案只要"本科"。

**原因**：大模型自由发挥，没约束输出格式。

**修复**：Pydantic模型改成枚举类型，只能填博士/硕士/本科/大专/高中之一；Prompt里加死规则。

**面试话术**：
> "我发现大模型输出学历太啰嗦，就用枚举类型约束，只能输出这5个值之一。这样评测时可以精确对比，不会因为输出格式不同而误判。"

**修复**：Prompt明确"按毕业年份到2026年计算"。

**面试话术**：

### Bug 9：skill准确率只有64%

**现象**：标注写英文"cross-border e-commerce"，模型输出中文"跨境电商"，对比时不一致。

**原因**：技能名中英文不一致，直接字符串对比不准。

**面试话术**：

### Bug 10：Pydantic中文键名映射

**现象**：大模型有时候返回`{"岗位名称": "AI工程师"}`而不是`{"job_title": "AI工程师"}`，导致Pydantic字段对不上。

**原因**：DeepSeek中文模型倾向于用中文键名。

**修复**：用Pydantic的`alias`参数：
```python
class JobMatchScore(BaseModel):
    job_title: str = Field(alias="岗位名称")
    score: int = Field(alias="匹配分数")
    reason: str = Field(alias="理由")
    
    class Config:
        populate_by_name = True
```

**面试话术**：
> "中文大模型经常返回中文键名，我用Pydantic的alias做了映射，既能接收中文键名也能接收英文键名，兼容性更好。"

### Bug 11：模型返回JSON数组而非对象

**现象**：大模型有时候直接返回`[{...}, {...}]`数组，而不是`{"matches": [{...}]}`对象。

**原因**：模型理解不一致，prompt里写的格式它没完全遵守。

**修复**：加`isinstance`判断：
```python
parsed = json.loads(text)
if isinstance(parsed, list):
    parsed = {"matches": parsed}
```

**面试话术**：
> "大模型有时候直接返回数组，我加了类型判断，如果是list就包装成dict，兼容两种输出格式。这是生产级代码必须做的容错。"

---

### Bug 12：f-string花括号转义

**现象**：prompt里写JSON示例，Python把`{`当成变量替换，运行报错。

**原因**：f-string里`{}`是变量占位符，JSON示例里的花括号会被误解。

**修复**：JSON示例里的花括号写成`{{}}`双花括号，Python会转义成单花括号。

**面试话术**：
> "f-string里写JSON示例有个坑，花括号会被当成变量。我用双花括号转义解决，这是Python字符串格式化的细节。"

### Bug 13：Windows GBK编码不认识特殊符号

**原因**：Windows控制台默认GBK编码，不支持Unicode特殊符号。

**修复**：用ASCII替代（OK/XX），或者设置`PYTHONIOENCODING=utf-8`。

**面试话术**：
> "Windows控制台默认GBK编码，不认识特殊符号。我用ASCII替代解决，跨平台兼容性更好。"

2. 加关键词召回补足：向量召回不足时，按技能匹配数补足

## P5.1阶段：A2 LLM打分硬规则——规则融合 + 硬上限（已完成）

### 现象
- P5评测5个错误案例中，R044段飞（机械结构工程师）是"召回第1但被LLM判到第2"——**LLM打分是概率性的，会翻车**。
- 评测还暴露一个技术债：`scoring_rules.py`里的权重表 `SCORING_RULES` 从P1起就从未被真正读取（nodes.py只import没用）。

### 原因
1. LLM打分纯自由发挥，没有确定性兜底：核心技能完全不沾边的岗位也可能被打70-90分
2. 权重表只是"配置"，没有变成"代码"——四维打分停留在prompt文本里，不可复现、不可测试

### 修复（A2，已实施）
1. **scoring_rules.py从"死配置"升级为"规则引擎"**：
   - `compute_rule_score()`：纯代码确定性打分（技能40/学历10/年限30/项目20，读SCORING_RULES权重）
   - `hard_cap()`：硬上限——技能重合 0→25分、1→40、2→60、3+→不限
   - 技能归一化 `SKILL_SYNONYMS`（中英文同义词），和eval_runner同一套
2. **nodes.py加 `_fuse_scores()`**：最终分 = `min(0.5×规则分 + 0.5×LLM分, 硬上限)`，成功/重试两个分支统一走融合
3. **修复隐藏Bug"融合被绕过"**：LLM把部门名抄进岗位名（`AI Agent工程师（产品部）`），映射表查不到裸标题→融合走兜底没生效。加 `_normalize_job_title()` 剥离 `（…）` 后缀，离线验证修复生效

## P7阶段：抽取层加固——非技术技能补抽（已完成）

### 现象
- P6 后唯一确认的真问题是 R015（外贸业务员）：真命岗位 rank -1（召回漏），最终 Top-3 卡在 98%。
- 抽取体检发现：LLM 抽取技能时会**系统性忽略非技术技能**——语言（英语）、行业运营（跨境电商）、内容技能（AIGC内容生成）全部漏抽，漏抽率 2.5%。

### 原因
1. 抽取 prompt 第4条只写"技术栈列表"——LLM 把"技能"理解成"编程技术栈"，自动丢弃英语/跨境电商/内容运营等业务技能。
2. 这些词恰恰是区分"技术岗 vs 业务岗"的关键：R015 简历有 `英语(CET-6), 跨境电商运营`，漏抽后检索 query 只剩 `Python/SQL/数据分析`，外贸岗根本进不了候选。

### 修复
1. **抽取 prompt 强化**：明确要求 skill 覆盖四类——技术栈、语言能力、行业/业务技能、专业软技能，逐项从原文提取、不自创不合并。
2. **确定性补抽保险**：抽取后自动对比简历原文「技能：」/「技术栈：」行，原文有但没抽出的技能直接补回。**不赌 LLM 自觉**，原文是唯一客观事实。
3. 新增 `eval/extraction_audit.py`：把"原文技能 vs 抽取技能"逐词对比，量化漏抽率，作为抽取层的回归测试。

### 效果验证
| 指标 | P6 | P7 |
|---|---|---|
| Top-1 | 76.0%（38/50） | **78.0%（39/50）** |
| Top-3 | 98.0%（49/50） | **100.0%（50/50）** |
| 抽取漏抽率 | 2.5%（6词） | **0%（0词）** |
| 评测成功率 | 50/50 | 50/50 |

- R015：rank -1 → 2（召回漏修复）
- R043：2 → 1；R028：3 → 1；R039：2 → 1
- R007/R026：1 → 2，查明是"两个岗位都合理"的语义歧义（Video-LLM→视频算法/CV、5G协议栈→通信/嵌入式），均在 Top-2，不是错误。

### 关键认知
1. **抽取是整条链路的源头**：源头漏一个技能词，检索 query 就少一个特征维度，下游再强也救不回来。
2. **prompt 解决"理解偏差"，代码兜底"执行不稳"**：prompt 告诉 LLM 该抽什么，确定性补抽保证"原文有的一个都不丢"。两者是互补，不是替代。
3. **Top-3 100% 意味着召回与粗排已完全够用**，剩余全部是语义细粒度区分问题。

### 面试话术
> "抽取是整条链路的源头。我做抽取完整性体检时发现，LLM 会系统性地忽略非技术技能——比如外贸简历里的'英语、跨境电商'，它只抽 Python/SQL。我用了两层修复：prompt 里明确要求技能覆盖技术栈/语言/业务/软技能四类；同时在代码里加了一道确定性补抽——抽取结果必须覆盖简历原文的技能行，覆盖不到的直接从原文补回，不赌模型自觉。修完漏抽率从 2.5% 降到 0，Top-3 从 98% 提到 100%。这件事说明：prompt 负责'让模型理解对'，代码负责'保证执行稳'，两者互补。"

## P8阶段：职业身份信号——让系统"认人"（已完成）

### 现象
- P7 后 Top-1 卡在 78%，剩余失败全是"两个岗位胶着"：R004 金融产品经理、R013 内容策略产品经理、R042 交通产品负责人**全部输给数据分析师**。
- 原因不是技能不够：R004 的 LLM 分 92、R013/R042 项目相关度都判 AI产品经理更高，但规则层把"会 SQL/Python/数据分析"当成了数据分析师，硬上限 cap=60 把正确岗位物理压死。

### 原因
1. **技能重叠数 ≠ 岗位匹配度**：产品经理、研究员、设计师的 skill 表天然长着"数据分析师的样子"（SQL/Python/数据分析），字面重合规则只看技能不看**身份**。
2. **职业身份是简历里最强、也最客观的信号**：候选人最近一段工作的职位名称（career），直接回答"他是干什么的"。此前的评分链路（规则分、LLM 分、重排文本）都没用它。

### 修复
1. **抽取层**：`ResumeInfo` 新增 `career` 字段，抽取 prompt 第4条强制提取"最近一段工作经历的职位名称"，fallback 分支 `setdefault("career","")` 兜底。
2. **规则层**：新增 `ROLE_SYNONYMS`（职位词→职能类别映射）+ `career_match_score`（候选人 career 与岗位 title 职能类别交集→20分），加入 `compute_rule_score`。
3. **硬上限升级（关键）**：`hard_cap` 从"只认字面重合数"改为"**职业身份匹配的岗位不再被重合数误伤**"——career 与岗位职能一致时 cap=100。R004 AI产品经理 rule 60→78、R039 纺织面料 rule 40→71，不再被 cap 压死。
4. **重排层**：`build_resume_text` 把 career 拼进简历文本，让 cross-encoder 也看到真实职位。
5. **打分 prompt**：新增"职业身份优先"原则，职能岗不因"会 SQL"被技术岗顶掉。

### 效果验证（在错误标答上跑过，数字不可信——见P9）
P8 当时在"模型输出导向"的错误标答上验证，Top-1 报过 94%，**作废**。P8 的价值在代码层的身份信号，真实基线见 P9。

### 关键认知
1. **身份 > 技能重合**：招聘匹配的核心是"这个人是谁、干什么的"，不是"他会哪几个词"。职业身份是比技能更硬的信号。
2. **硬上限的语义**：cap 应该挡"不相关岗位"，不能误伤"字面重合少但职业匹配"的相关岗位——识别"相关"要靠多维信号，不能只看单一字面维度。

### 面试话术
> "我发现 Top-1 卡在 78% 的瓶颈是'两个岗位胶着'——金融产品经理、内容策略产品经理总是输给数据分析师。分析后发现：产品经理的技能表天然长着数据分析师的样子（SQL/Python/数据分析），字面重合规则只看技能不看身份。我在抽取层加了'最近一段工作职位'字段，规则层用职位词→职能类别映射做了职业身份匹配加分，并把硬上限从'只认字面重合数'升级为'职业身份匹配的岗位不被误伤'。这轮的核心认知是：招聘匹配首先要回答'这个人是谁'，职业身份是比技能重合更硬、更客观的信号。"

2. **对照验证**：机器人算法岗 career=0 不误伤，非目标岗位不受影响。
3. R042 明确不动——弱标答，强行修会让评测迁就模型，违背客观原则。

### P9.1 最终结果
| 指标 | P9 | P9.1 | 变化 |
|---|---|---|---|
| Top-1 | 94.0%（47/50） | **98.0%（49/50）** | +2 |
| Top-3 | 100.0%（50/50） | **100.0%（50/50）** | — |
| 未登顶 | R015/R024/R042 | **仅 R042（弱标答）** | R015✓ R024✓ |
| 评测成功 | 50/50 | 50/50 | — |

- R015：rank2→1（补 `海外运营→跨境` 职能映射）
- R024：rank2→1（补 `自助驾驶→自动驾驶` 错别字容错）
- R042：保持 rank2（交通产品负责人 vs AI产品经理，行业域不符的弱标答，不修）

### 关键认知
1. **评测集是需要版本治理的数据资产**：标答是 ground truth，必须可追溯、可复核、基于客观证据。任何"为了指标好看"的改法都是自我欺骗。
2. **磁盘状态 ≠ 评测状态**：评测进程启动时读一次标答进内存，之后文件改了评测不知道。修标答后必须重跑评测，不能只看日志。
3. **"要客观"的落地检查**：每次改动后自问——这个改动是让系统更接近事实，还是让标答更迁就系统？

### 面试话术
> "我复盘评测流程时发现一个隐蔽问题：标答文件被改坏了——22 份置空，还有一批标答被改成了'模型爱输出什么就标什么'，比如轮机工程师被标成外贸业务员。评测脚本对空标答直接跳过，导致表面上跑 50 份、实际只评 28 份。我把标答当作数据资产治理：以 git 历史里的客观版本为基准恢复，逐份把'简历工作经历职位 vs 标答'并排复核，并加脚本校验每个标答都能命中岗位库。修完后跑出第一个可信基线 Top-1 94%。这件事的教训是：**标答是 ground truth，不是可调参**——一旦为了让指标好看去改标答，评测就从'测系统'退化成'测自己愿不愿意迁就模型'。"

## P10阶段：排序质量指标——MRR / NDCG（已完成）

### 现象
- P9.1 后 Top-1 98%、Top-3 100%，二值指标已到天花板。但 Top-1/Top-3 只问"正确岗位进没进前K"，**排第2 和排第40 对指标毫无区别**——真实推荐系统里，正确岗位排第2 和排第40 是天壤之别。

### 解法
新增 `eval/metrics.py`，把评测日志的 rank 转成两个排序质量指标：
- **MRR**（平均倒数排名）：rank=1→1.0、rank=2→0.5、rank=3→0.33、召回漏→0。衡量"正确岗位离 Top-1 有多近"。
- **NDCG@K**（归一化折损累计增益）：单标答下 rank=1→1.000、rank=2→0.631、rank=3→0.500、召回漏→0。衡量"整体排序质量"。
- 自动集成：`eval_match_v2_batch.py` 本批跑完自动从日志解析 rank、打印 MRR/NDCG，评测闭环（评测→指标→归因→修复→再评测）完整。

### 效果验证（P9.1 基线）
| 指标 | 数值 | 说明 |
|---|---|---|
| Top-1 | 98.0% | 49/50 |
| Top-3 | 100.0% | 50/50 |
| **MRR** | **0.9900** | 唯一丢分点 R042（rank2） |
| **NDCG@3** | **0.9926** | 同上 |

- 排序质量几乎满分，剩余丢分全部来自 1 个故意不修的弱标答（R042）。
- **这一步到这是"知道何时该停"**：MRR 0.99 已无法提供更多区分度，继续磨排序边际收益极小。P10 的价值是让评测方法论闭环、并在面试里展示"我不仅看 Top-1，还看排序质量"。

### 面试话术
> "Top-1 到 98% 后我发现一个问题：二值指标只问'对不对'，不问'排得准不准'。真实推荐系统里正确岗位排第2 和排第40 是天壤之别。所以我把评测升级成排序质量指标——MRR 和 NDCG：正确岗位排第1贡献1.0、排第2贡献0.5、排第3贡献0.33，召回漏计0。集成进评测脚本自动算，当前 MRR 0.99、NDCG 0.993。这件事的收获是：**指标要和业务目标对齐**——Top-1 告诉你能不能找到，MRR/NDCG 才告诉你能不能排准；而且要知道何时停，指标满到没有区分度就该换维度。"

## P12阶段：可解释报告——把分数翻译成人话（已完成）

### 现象
- P11 之后用户看到的是"86 分"这个数字，但说不清这个数字怎么来的、缺什么、为什么不是另一个岗位。产品/应用开发岗面试时，光有高准确率不够——**"为什么"比"是多少"更能证明系统不是黑盒**。

### 解法（`explain.py` 新增解释层）
- 新增 `/api/v1/match` 响应字段 `explanation`：
  - `summary`：Top-1 总评段落（候选人职业身份 → 岗位 → 分数 → 技能重合/硬性缺口 → 三路信号一致度 → 硬上限提醒）
  - `per_job`：每个岗位的逐项解读（`verdict` 强/中/边缘/不匹配 + 职业身份/年限/学历/硬上限 四行 + 技能命中/缺口 chips）
- **原则：解释层的事实全部确定性计算，零 LLM 幻觉风险**：
  - 技能重合/缺口 → `skill_overlap`（规则引擎）
  - 职业身份/年限/学历/硬上限 → `career_match_score` / `EDU_RANK` / `hard_cap`
  - 总评段落 → 模板 + 事实拼接，不经过 LLM 措辞发挥
- 关键设计决定：
  - **缺口只取岗位原始 `required_skills`**，不取 `JOB_SKILL_EXPANSION` 扩充域（扩充域是算法补的行业知识，拿来当"你必须会"不够客观）
  - 规则分在 API 层计算一次并缓存回 score dict（`rule_score`），解释层复用，不重复算
- 前端：新增「匹配解读」Tab（默认打开），每张岗位卡内嵌 ✓命中 / +缺口 技能标签，替换原「信号明细」为独立 Tab 保留四信号数字表。

### 过程中修的 bug
- 解释层自测发现：`career=AI Agent工程师` 在职能类别里命不中「AI Agent工程师」岗位（ROLE_SYNONYMS 无 agent/工程师类目），`career_match_score=0`——这是**现有系统的真实行为**，解释层如实呈现（总评不夸大、per_job 诚实标注"职能不匹配"），没有为了让话术好看去改同义词表。加了命中 career 的对照用例验证 +20 分支。

### 效果验证
- 确定性自测：用例1（无 career 加分）与用例2（career 命中 → verdict 带"职业身份一致"、career 行 +20）均通过（`python explain.py`，不调 LLM/向量库）
- 端到端回归：`python eval/check_explain.py` 走真实流水线，不变量校验通过：per_job 数量==matches 数量、每岗位有 years/education/career 解读、hit/gap 为列表
- 新增 `eval/check_explain.py` 作为解释层回归测试（防解释层与匹配结果漂移）
- **回归时发现的信号分歧案例（记录待查，非本轮修复范围）**：张明简历（LangGraph/RAG/Milvus/Prompt 工程/AI客服Agent 项目）在两次独立运行中 Top-1 在 AI Agent工程师 86 与 NLP算法工程师 85 之间**翻转**（回归测试跑出 NLP85，HTTP 冒烟跑出 AI Agent86）。两岗分数只差 1 分：AI Agent 赢在技能重合 5 项但 career 不匹配，NLP 赢在 career+20 但只重合 2 项。说明 LLM 抽取/打分波动会让伯仲之间的岗位翻车。属 P11 修 bug 前已存在的现象，非解释层引入。按"要客观"原则不 tune，留作 P13 候选（稳定性：同简历跑 N 次统计 Top-1 方差 / temperature=0 / 多数表决）。

### 关键认知
1. **可解释性本身也要可解释**：解释层的每一句话都能追溯到一行代码算出来的事实（`skill_overlap`/`career_match_score`/`hard_cap`）——这是和"让 LLM 解释自己"最本质的区别。面试时这一句就是分水岭。
2. **诚实比漂亮重要**：career 命不中就是命不中，解释层如实说"职能不匹配"；用户看到的是可信，不是完美。
3. **确定性解释免费**：不经过 LLM，解释层零额外延迟零成本，还能保证解释与分数永远一致——"解释"不该是后补的故事，而是与决策同源的计算。

### 面试话术
> "高准确率之后我追问了一件事：系统说自己准，但它有没有能力说清楚**为什么**？我加了一层可解释报告：对 Top-1 岗位，用确定性计算生成总评——职业身份、技能重合几项、硬性缺口几项、三路信号一致度、硬上限有没有压分，每一句话都来自规则引擎的函数而不是大模型编理由。比如它会告诉用户'你缺 MCP，补齐可明显提分'，或者'你的职业身份与岗位职能不匹配'。关键是这层解释零 LLM 调用——**解释必须与决策同源**，如果解释是模型事后编的，那它就不是解释，是故事。前端我把解读做成默认 Tab，面试现场一份简历进去，先看到的是'为什么是它'，而不是一堆数字。"

## P13阶段：稳定性评测 + 在线评测台（已完成）

### 现象
- 张明简历两次运行 Top-1 在 AI Agent工程师/NLP算法工程师 之间翻转。单次评测的 Top-1 98% 是"跑对一次"，不代表"每次都跑对"。准确率高 ≠ 稳定。
- 评测只在命令行，跑一次 20-30 分钟；参数调完不能立刻看到指标变化，产品/应用开发岗面试时少一个"交互式演示"。

### 解法（两部分）
1. **稳定性评测**（`eval/stability_eval.py`）：同一简历重复跑 N 次，量化 Top-1 翻转率 / 标答跨重复命中率 / 分数波动，报告存 `eval/stability_*.json`。客观基线（before2，temp0.1）：
   - 5 份标答简历 × 3 次：**翻转 1 例（R001，AI Agent↔NLP，标答命中率 66.7%）**，R003/R015/R024 稳定、R042 稳定 rank2（弱标答，符合预期）
   - 张明压测：AI Agent 工程师 ↔ NLP算法工程师 翻转
   - **翻车源头是抽取层**：对比两次运行的抽取技能列表，NLP 命中项从 3 项变 2 项——LLM 每次抽的技能集合有波动
2. **在线评测台**（`/eval` 前端 + `/api/eval/*`）：
   - `eval/eval_cache.py`：跑一次全量流水线，缓存每岗位**四信号原始值**（rule/llm/rerank/cap）；`simulate()` 是纯函数，调权重只重算融合层——**毫秒级、零 LLM 调用**
   - 面板：Top-1/MRR/NDCG@3/召回 5 卡，3 根权重滑块（自动归一化）+ 硬上限开关 + 生产/仅规则/仅LLM/仅重排 预设，失败案例表；读 `stability_*.json` 展示稳定性
   - **所见即生产**：融合层抽成 `reranker.fuse_final()` 纯函数，面板与生产共用同一个公式

### 过程中修的 bug / 关键决定
- `manual_answers.json` 结构是 `{"说明":…,"answers":{R001:…}}`——stability_eval 一开始直接 `.get(rid)` 取不到标答（标答命中率一度 0.0%）。改成 `["answers"]` 子键后正常。
- 同一岗位带/不带部门后缀（`AI Agent工程师（产品部）` vs `AI Agent工程师`）不是翻转——比较前必须剥后缀。
- 降噪方案：`LLM_TEMPERATURE`（环境变量，0=最稳定）+ `SCORE_RUNS`（打分跑 N 次取**中位数**，默认1=关闭）。探测端点时发现短提示词下返回嵌套中文 JSON 无法验证 schema，故不赌 schema，直接在真实流水线上做 before/after 对比——客观证据优先于可复现实验。

### 效果验证（after：temp0 + 集成3）——结论：没修好，如实记录
同一批 5 份标答简历 × 3 次（`LLM_TEMPERATURE=0 SCORE_RUNS=3`）：

| 简历 | 标答 | 3 次 Top-1 | 命中率 | 分数波动 | 判定 |
|---|---|---|---|---|---|
| R001 | AI Agent工程师 | AI Agent / NLP / AI Agent | 66.7% | ±1 | 仍翻转 |
| R003 | 自动驾驶感知 | 自动驾驶 / CV / 自动驾驶 | 66.7% | ±3 | **新增翻转** |
| R015 | 外贸业务员 | 外贸 ×3 | 100% | ±9 | 稳定 |
| R024 | 自动驾驶感知 | 自动驾驶 ×3 | 100% | ±3 | 稳定 |
| R042 | AI产品经理 | 数据分析师 ×3 | 0%（稳定 rank2） | ±4 | 稳定（弱标答） |

- 汇总（只算有标答的 5 份）：**翻转 2/5 = 40%**（before2 是 1/5 = 20%）；标答跨重复命中率 **66.7%**（before2 73.3%）
- 张明压测：AI Agent 3/3，**稳定了**（before2 会翻转）
- **客观结论：temp0 + 打分中位数集成没有消除 Top-1 翻转，标答集上甚至更差。**
  - 降噪确实生效：R001 的 Top-1 分数波动从 ±6 收到 ±1
  - 但 R001 两个岗位只差 1 分（86 vs 85），降噪后仍是"擦边"，微小波动照样换位
  - R003 的翻转说明**抽取层方差没被 temperature=0 消掉**（该端点并非严格确定性）；打分集成只平均了打分噪声，平均不了抽取差异
- 为什么不继续加码：在 5 个样本上反复调参（如加 margin tie-break）就是过拟合，违背"标答只来自客观事实、不为指标调参"的原则。真正的解法是**全流水线集成**（抽取也跑 N 次做投票/中位数）或抽取层规则兜底，成本 ×N，留作后续。当前两个开关默认关闭，不把"分数波动下降"包装成"稳定性提升"。

### 关键认知
1. **评测要测两层**：准确率（对不对）和稳定性（每次对不对）。单点快照会被运气欺骗。
2. **交互式评测台就是"把评测过程变成产品"**：缓存信号原值 + 融合层纯函数，让"我调完参数指标立刻刷新"成立——这不是demo动画，是真实数据上的实验。
3. **调参不该烧 LLM**：重算融合层毫秒级，因为 LLM 只负责"从文本里读信号"，融合是确定性数学。
4. **负结果也是结果**：temperature=0 + 打分集成降低了分数方差，但没有消除 Top-1 翻转（标答集 1/5 → 2/5）。根因是抽取层方差 + 近分岗位，不在打分层。如实记录，不把降噪说成稳定性提升——这比编一个"修好了"的故事更能说明我知道系统边界在哪。

### 面试话术
> "Top-1 98% 之后我做了第二层体检：准确率是'跑对一次'，稳定性是'每次都跑对'。我把同一份简历重复跑 3 次，发现张明这类算法工程师简历会在 AI Agent 和 NLP 两个岗位间翻转。我先假设是 LLM 随机性，做了两个修复：温度降到 0，打分跑 3 次取中位数。结果**没修好**——翻转率从 1/5 变成 2/5。但数据告诉了我为什么：分数波动确实从 ±6 降到 ±1，可那两个岗位只差 1 分，降噪之后还是擦边；另一份简历的翻转则来自抽取层，temperature=0 并没有让抽取变确定。所以我判断瓶颈不在打分层，而在抽取层的方差，真正的解法是全流水线集成或抽取层规则兜底，成本 ×N，我没有为了指标在这 5 个样本上继续调参。同时我把整个评测做成了在线面板：先跑一次全量流水线，把每个岗位的四信号原始值缓存下来；之后拖动权重滑块，只重算融合层这个纯函数，MRR/NDCG 毫秒级刷新——**调参不烧 LLM，因为 LLM 只负责读信号，融合是确定性数学**。这轮最大的收获不是把指标做高，而是知道系统在哪一层会翻车、以及诚实汇报一个失败的修复。"
